2023년에는 카카오 테크 캠퍼스에서 교육을 받았습니다.  
오늘은 카카오의 클라우드 기반 학습 관리 시스템인 크램폴린 환경에 배포하며 겪은 문제를 나누려고 합니다.

> [!note] 2026년의 메모
> 이 글은 2023년 12월에 썼습니다. 2년 뒤에 다시 읽으며 문장을 다듬고, 지금의 제가 보기에 달리 했을 부분을 이런 메모로 덧붙였습니다. 당시의 판단과 순서는 고치지 않고 그대로 두었습니다.

## Intro. 무슨 일인가

카카오 테크 캠퍼스 3단계 프로젝트의 주제는 축팅(네 컷 사진을 통해 축제에서 자연스러운 만남을 주선하는 서비스)이었습니다.

사진 업로드 기능을 배포 환경에서 테스트하니 Nginx `413 Request Entity Too Large` 에러가 발생했습니다.

찾아보니 요청 본문 크기 제한의 기본값이 1M라서, 이 값을 늘리면 되는 문제로 보여 금방 다시 배포했습니다.  
하지만 문제는 해결되지 않았습니다.

> [!note] 2026년의 메모
> 2023년의 저는 에러 메시지를 검색하고 곧바로 설정값을 고쳤습니다. 지금이라면 값을 바꾸기 전에 "이 413을 누가 돌려줬는가"부터 확인했을 겁니다. `curl -v`로 큰 파일을 보내 응답 헤더와 에러 페이지를 보는 데는 1분이면 충분합니다. 이 질문을 건너뛴 탓에 아래의 시도들은 전부 엉뚱한 단을 고치는 일이 되었습니다.

> - Nginx 413 에러란?
>   - 의미: 요청 본문(body)이 서버가 허용한 크기보다 크다
>   - Nginx는 `client_max_body_size`(기본값 1m)를 넘는 요청을 본문을 다 받기 전에 거절한다
>   - 지나치게 큰 업로드가 디스크와 메모리를 채워 서비스가 내려가는 일을 막기 위한 제한이다
>   - 최신 HTTP 표준(RFC 9110)에서는 이름이 `413 Content Too Large`로 바뀌었다

## 원인 파악

![크램폴린 IDE 배포 플로우와 시스템 연동기능 관계도](/_attachments/tistory-546-01.png)

원인을 파악하려면 크램폴린의 배포 플로우를 다시 떠올릴 필요가 있었습니다.  
크램폴린 IDE의 배포는 쿠버네티스 환경에서 진행되기 때문입니다.

D2Hub에서 이미지를 빌드하고, Kargo로 DKOS 클러스터에 애플리케이션을 배포하는 흐름을 보면 알 수 있습니다.

> - Kargo
>   - 크램폴린에서 DKOS(쿠버네티스) 클러스터에 애플리케이션을 배포하는 도구
>   - 클러스터 설치 도구인 Kubespray도 예전 이름이 Kargo였다. [이름이 같아 헷갈리기 쉽지만](https://somaz.tistory.com/72) 서로 다른 도구다

> [!note] 2026년의 메모
> 그림을 다시 꺼내 본 것까지는 좋았는데, 정작 그림에서 읽어야 할 것을 읽지 못했습니다. 이 구조에서는 요청이 제 Pod에 닿기 전에 **제가 관리하지 않는 프록시**를 먼저 지납니다. 413은 요청 경로에서 제한을 넘긴 첫 번째 프록시가 돌려주므로, 뒤쪽 설정을 아무리 늘려도 앞단의 제한이 그대로면 결과는 같습니다. 당시에는 이 사실을 모르고 제 쪽 설정부터 의심했습니다.

### 1. 쿠버네티스 환경에서 Nginx 설정이 잘못되었는가?

쿠버네티스 환경에서 Nginx 설정을 바꿀 수 있는 경로는 2가지입니다.

1. **인그레스 컨트롤러(ingress controller) 설정**
   - NGINX 인그레스 컨트롤러에 어노테이션(annotation)으로 Nginx 설정을 적용
2. **NGINX 설정 커스터마이징**
   - NGINX의 설정 파일인 `nginx.conf`를 직접 수정한 Pod을 생성

#### 1-1. 인그레스 컨트롤러(ingress controller) 설정 조절

쿠버네티스의 인그레스 컨트롤러는 외부 요청을 클러스터 내부 서비스로 라우팅하는 역할을 합니다.

먼저 카카오 크램폴린에서 기본으로 제공하는 Nginx를 사용하고, 기존에 제가 설정한 관련 Pod들을 제거했습니다.

그 후 body size를 조정했습니다.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: example-ingress
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: "64m"
spec:
  rules:
  - http:
      paths:
      - path: /example-path
        pathType: Prefix
        backend:
          service:
            name: example-service
            port:
              number: 80
```

하지만 여전히 문제는 해결되지 않았습니다.

#### 1-2. NGINX 설정 커스터마이징

NGINX 설정을 직접 수정하는 경우, `nginx.conf` 파일을 수정해 Pod에 적용할 수 있습니다.

```nginx
http {
    …

    client_max_body_size 64M;

    …
}
```

ConfigMap으로 설정을 주입해 보고, Nginx 이미지를 직접 패키징하면서 설정 파일을 넣어 보기도 했지만 여전히 문제는 해결되지 않았습니다.

> [!note] 2026년의 메모
> 두 방법 모두 "설정이 적용되지 않았을 것"이라는 가정 위에서 방법만 바꿔 본 시도였습니다. 지금이라면 가정부터 검증했을 겁니다. 클러스터에 접근할 권한이 있다면 두 가지를 확인합니다.
>
> - 설정이 실제로 적용되었는가: `kubectl exec <nginx-pod> -- nginx -T | grep client_max_body_size`
> - 앞단을 건너뛰면 통과하는가: `kubectl port-forward`로 제 Nginx에 직접 붙어 큰 파일을 보내 본다
>
> 두 번째 실험에서 업로드가 통과하면 범인은 제 Pod 바깥에 있습니다. 설정을 세 번 고쳐 배포하는 것보다 훨씬 싸게 탐색 범위를 절반으로 줄일 수 있습니다.

### 2. 로그 확인: Hint 발견

Nginx Pod을 띄우면 1M 이하의 이미지는 받아지고, 용량을 넘는 경우에만 Postman에 에러가 돌아왔습니다. 이미지 크기 제한 문제인 것은 확실했습니다.

Pod 로그를 확인해 보니, 다른 API 엔드포인트에 대한 요청은 로그로 남는데 413 에러만 빠져 있었습니다.

Nginx Pod에 사용한 이미지는 바디 사이즈만 조절한 것이라 로그가 빠질 이유가 없었습니다.

Nginx가 413을 돌려줄 때는 에러 로그에 `client intended to send too large body`라는 줄을 `error` 레벨로 남깁니다. 기본 Docker 이미지의 로그 설정으로도 충분히 기록되는 레벨입니다. 그러니 제 Nginx가 요청을 거절했다면 이 줄이 반드시 남아 있어야 했습니다.

제가 구성한 인프라의 문제가 아닐 수 있다는 의심이 들었습니다.

> [!note] 2026년의 메모
> 이 글에서 가장 잘한 부분입니다. "있어야 할 로그가 없다"는 것도 증거입니다. 로그에 이 줄이 없다는 것은 요청이 제 Nginx에 **도착조차 하지 않았다**는 뜻이고, 여기서 사실상 답이 나왔습니다. 다만 2023년의 저는 이것을 "수상하다" 정도로만 받아들였습니다. 로그를 첫 단계에서 봤다면 앞의 두 시도는 필요 없었을 겁니다.

### 3. 로컬에서 동일한 환경 구성 후 테스트

의심되는 이미지(바디 사이즈를 조절한 기본 Nginx 이미지)를 로컬에서 테스트해 보았습니다.

- 재현 방법
  - 기존의 NGINX 이미지 생성 후 로컬 BE 프로젝트에 연결
  - 8081로 NGINX 연결하고, Postman으로 큰 이미지 전송
  - NGINX 통과 후 BE 프로젝트 예외 반환 확인!

![로컬 NGINX 컨테이너 로그: 큰 이미지 요청이 NGINX를 통과해 백엔드에서 401을 반환](/_attachments/tistory-546-02.png)

큰 이미지가 Nginx를 통과해 백엔드까지 도달했으니, 제가 만든 이미지의 문제가 아니었습니다.

> [!note] 2026년의 메모
> 변수를 하나만 남기고 재현한 좋은 실험입니다. 로그의 `401`은 인증 없이 보낸 요청을 백엔드가 거절한 것이니, 본문이 Nginx를 통과했다는 증거가 됩니다. 한 가지 한계는, 이 실험이 증명하는 것은 "이미지가 정상"까지라는 점입니다. 클러스터 안에서 그 이미지가 같은 설정으로 돌고 있는지는 따로 확인해야 합니다.

> [!note] 2026년의 메모
> 아래 "깨달은 점"은 지금 읽어도 고칠 것이 없습니다. 하나만 보태자면, 일정이 밀린 원인은 문의가 늦어서라기보다 순서에 있었습니다. 요청이 지나는 경로를 먼저 확인하고 설정은 그다음에 바꿨어야 했습니다. 2023년의 저는 고칠 수 있는 곳부터 고쳤고, 지금의 저는 어디가 고장 났는지부터 좁힙니다.

- 깨달은 점
  - 인프라처럼 당연해 보이는 것들도 합리적으로 의심할 필요가 있다
  - 협업 상황에서는 문제의 진행 상황을 공유하고, 적절한 시기에 시니어에게 도움을 요청하자
    - 될 때까지 잡고 늘어지다 개발 일정이 밀리는 것은 일을 잘한다고 할 수 없다

2년 전의 제게, 그리고 같은 문제를 만난 분께 아래 순서를 권합니다.

- 413을 돌려준 주체부터 확인한다
  - 내 Nginx의 에러 로그에 `client intended to send too large body`가 없으면, 거절한 것은 내 Nginx가 아니다
  - 응답 헤더의 `Server` 값과 에러 페이지 모양도 어느 단이 응답했는지 알려 주는 단서다
- 요청이 지나는 프록시를 바깥에서 안쪽 순서로 모두 적어 본다
  - 본문 크기 제한은 경로 위의 모든 프록시에서 각각 풀어야 한다
- 내가 권한을 갖지 않은 단이 원인이면, 로그와 재현 결과를 정리해 관리자에게 빨리 문의한다

## 궁금했던 점

### proxy-body-size와 client_max_body_size의 차이

> [!note] 2026년의 메모
> 2023년의 저는 이 절에 "하나는 클라이언트 요청을, 다른 하나는 업스트림으로 가는 요청을 제한한다"고 적었습니다. 그럴듯하지만 틀린 설명이었습니다. 문제는 해결했어도 원리는 이해하지 못한 채 글을 닫았던 셈이라, 이 절은 새로 썼습니다.

결론부터 말하면 둘은 **같은 제한이고, 설정하는 위치만 다릅니다**.

1. **client_max_body_size**
   - Nginx의 실제 지시어(directive)입니다. 클라이언트 요청 본문의 최대 크기를 정합니다.
   - `http`, `server`, `location` 블록에 쓸 수 있고, 기본값은 `1m`입니다. `0`으로 두면 크기 검사를 하지 않습니다.
   - Nginx가 프록시로 동작할 때도 똑같이 적용됩니다. 프록시도 결국 클라이언트의 요청을 먼저 받기 때문입니다.
2. **proxy-body-size** (어노테이션: `nginx.ingress.kubernetes.io/proxy-body-size`)
   - Nginx 지시어가 아니라 쿠버네티스 커뮤니티의 ingress-nginx 컨트롤러가 받는 설정 이름입니다. Nginx에 `proxy_body_size`라는 지시어는 없습니다.
   - 컨트롤러는 이 값을 읽어, 자신이 생성하는 `nginx.conf`의 `client_max_body_size`로 옮겨 적습니다.
   - 어노테이션은 해당 Ingress에만, 컨트롤러 ConfigMap의 `proxy-body-size` 키는 전체에 적용됩니다. 기본값은 마찬가지로 `1m`입니다.

#### 결론

- **직접 운영하는 NGINX 서버의 경우**
  - `nginx.conf`에서 `client_max_body_size`를 설정합니다.
- **쿠버네티스 인그레스 컨트롤러(ingress-nginx) 사용 시**
  - `nginx.ingress.kubernetes.io/proxy-body-size` 어노테이션을 사용합니다. 컨트롤러가 이 값을 `client_max_body_size`로 바꿔 적용합니다.
- **프록시가 여러 겹인 경우**
  - 가장 작은 제한이 전체의 제한이 됩니다. 이 글의 문제도 제 설정이 아니라 그 앞단의 제한 때문이었습니다.
